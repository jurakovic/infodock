# Architecture review findings

From the M5 architecture review (plan item S14a, D79): four clean-context reviewers on the whole tree at `f3297a9`, 2026-10-21, one per area: the bar; the sensor framework and the sensor types; the platform layer, providers and sampler; Settings, config and the app's wiring. Unlike the milestone reviews (`review-m1.md`–`review-m4.md`), which looked for defects in each milestone's diff, this one looks at structure: SOLID, module boundaries and dependencies, trait design, design patterns, duplication, oversized files and types, naming, readability, testability, and consistency with `CLAUDE.md`'s conventions.

Each finding is checked against the code and weighed against what a change costs this close to the release. Those worth changing are grouped into plan items (S14b…); the others are listed under *Not changed* with the reason. Line numbers are as of `f3297a9`.

Findings are numbered by area (B the bar, S sensors, P platform, providers and sampler, C Settings, config and the app) so plan items can name them. Each gives severity (High: slows or endangers changes now; Medium: real but contained; Low: polish), effort (S under half a day, M about a day, L more or risky) and the reviewer's recommendation; the decision for each is made when all four areas are in, under *Plan* below.

Status: the bar and Settings/config are in and checked (counts and line references spot-checked: `BarLogic`'s fields, the `Env` literals, `drop.rs`, the slide-out rule, the zone orders, the `WINDOW` sites, the Slint page literals and settings paths, `ConfigError`, the store's lock); sensors and platform are still running.

## The bar (`src/bar`)

### Strengths

- Pure logic lives in small tested modules outside the bar thread (`layout`, `placement`, `interact`, `focus`, `resize`, `anim::Fade`, the menu and tray builders, `drop::classify`, `shadow`, `theme`, the skins): 120 of the area's 167 tests are outside `thread.rs`. `hint::Hover` is a state machine that returns `Step` effects for `thread.rs` to apply.
- `BarLogic` is platform-free behind `BarWindow`, `BarHandler` and `BarHost`; 47 tests drive it end to end on Linux with fakes and the recording canvas.
- One cross-thread pattern: `BarController` queues a `Command` and wakes the thread; every config change the bar makes goes through the store and comes back as `Command::Config` (§4.4), so there is one source of truth.
- Modern vs. classic is decided once, in `Theme::resolve`, and turned into data; `paint_bar` has a single path.
- `BarSensors` is the only code that touches `dyn Sensor`; sensors return effects as values (`ClickResult`, dirty flags, `take_state`/`take_props`). `IconSource` is defined in `sensors` and implemented by the bar's worker: dependency inversion done right.
- No `unwrap`/`expect` and no OS calls in non-test bar code; errors are typed and localised (`PackError::message`, `InstallError::message`).

### Findings

- **B1 Medium — `BarLogic` (`bar/thread.rs:112`) does about 12 jobs: 41 fields, 64 methods, 2,013 lines of code and 2,220 of tests in one file.** Effort M; reviewer: before 1.0, stage 1 only. The largest file in the tree and the bar's hotspot (14 of the last 51 commits). Its jobs by line range: state and construction 112–287; tray 289–321; pointer gestures 323–553 and 778–886 (`pointer_moved` alone 100 lines); bar motion 555–608, 645–665; config and theme 610–643, 1194–1214; hover hint 667–776, 1483–1498; context menus 888–1001 (`menu` is 98 lines building, showing and running 15 commands); popup hosting 1003–1192; sensor lifecycle 1216–1388; external drag & drop 1391–1553; keyboard and UI Automation 1555–1736, 1989–2011; dispatch and painting 1738–1983 (`on_event` 133 lines). **Proposal, stage 1 (mechanical):** `thread.rs` becomes `thread/mod.rs` (struct, `new`, dispatch, config, tray) with child modules `pointer`, `hover`, `menu`, `popups`, `sensors`, `external_drop`, `keyboard`, `frame`, moved unchanged (children see the parent's private fields, so no visibility changes); tests split the same way under `thread/tests/` with the fakes in `tests/mod.rs`. **Stage 2 (after 1.0):** the pointer's five `Option`s (`press`, `drag`, `moving`, `resizing`, `external`), whose exclusivity only the order of checks in `pointer_moved` (399–466) and `pointer_up` (817–838) enforces, become one `Gesture` enum; `shown`, `highlight`, `rise_pending`, `sliding_out` and `slid` a `Motion` type returning effects like `Hover`.
- **B2 Medium — `bar` and `sensors` depend on each other, and Settings reaches into `bar`.** Effort S; reviewer: before 1.0. Sensor files import `bar::theme::Theme` (27 imports, e.g. `sensors/mod.rs:47`, `common/meter.rs:10`), `sensors/spacer.rs:12` imports `bar::anim`, `sensors/mod.rs:266` calls `bar::clicks_allowed`; Settings uses `bar::skins` and `bar::skin_preview` (`settings/appearance.rs:15–17`, 220, 395), and `skins/install.rs` and `skins/zip.rs` (650 lines) run only from Settings, on the main thread. **Proposal:** move `bar/theme.rs`, `bar/skins/` and `bar/anim.rs` to a neutral top-level module (e.g. `src/look/`); `clicks_allowed` becomes `Settings::clicks_allowed(alt)`; `skin_preview` stays. About 30 import lines plus §4.2's module tree; dependencies then run bar → sensors → look/platform and Settings → look. Same as C-x1.
- **B3 Medium — `bar/drop.rs:63–73` hard-codes three sensor types and their prop keys, untested against their schemas.** Effort S; reviewer: before 1.0. `("disk", drive)`, `("folder-menu", folder)`, `("shortcut", target | url, title)`: a renamed prop is caught only at runtime by `ops::add` in `App::add_sensors` (`app.rs:194–216`), which rejects the whole drop with a log line; the bar's drop test goes through `FakeHost`, which validates nothing. **Proposal:** move `new_sensor` beside `Dropped` in `sensors/drop.rs` (the bar keeps `classify`), name the types through their modules' constants, and test every result through `ops::add` with the real registry.
- **B4 Medium — the same context and presentation plumbing is written out repeatedly in `thread.rs`.** Effort S; reviewer: before 1.0, with B1. `Env { … }` is built 12 times at runtime (532, 713, 863, …, 1990) and 9 more in tests, identical but for `alt`, so a new field means 21 edits; `PopupCtx` (14 fields) twice (1047, 1144); `self.hover.dismiss()` + `apply_hint` 14 times; the hint pipeline (content → `HintBody` → `HintFrame` → `physical_rect` → show/paint) 4 times (`thread.rs:731`, 1489; `paint.rs:706`, 1395); the popup delays' `Duration::from_millis` 3 times. The literals exist because a `&self` method returning `Env` would borrow all of `self` while `self.sensors` is borrowed mutably. **Proposal:** a `Shared` sub-struct (`settings`, `theme`, `platform`, `animate`, `changes`) with `fn env(&self, alt)` (disjoint borrows), or a local `env!` macro; `dismiss_hint`; a `hint::Prepared` used by `thread.rs` and the screenshot harness; `PopupSettings::{show_delay, hide_delay}`.
- **B5 Low — "a docked bar that changes edges slides out first" is written twice, on two threads.** Effort S; reviewer: before 1.0. `bar/mod.rs:149` (the store listener skips the redock) and `thread.rs:621` (starts the slide-out, then redocks) must agree, or the bar redocks twice or never. **Proposal:** one pure `slides_out(old, new)` in `anim.rs`, used by both, with a test.
- **B6 Low — menu commands run in two places, and Settings routes cross as formatted strings.** Effort S; reviewer: after 1.0. `TrayCommand` (`tray.rs:9`) and `MenuCommand` (`menus.rs:12`) overlap (Lock, Popups, Settings, Quit) with duplicated closures (`thread.rs:311–317`, 976–982); routes are formatted at `thread.rs:944–975` (`"new?zone={}&index={}"`, `"sensor/{id}"`) with `zone_id` (`thread.rs:104`), a third copy of the zone names, and parsed back by `settings::model::route`, which opens General on anything unknown. **Proposal:** `BarHost::open_settings(Route)` with `Route` in a neutral module; one `run(MenuCommand, …)` with the tray's toggle folded in. Same as C12.
- **B7 Low — the bar's chrome is drawn in four files, and the screenshot and budget harness assembles the frame itself.** Effort M; reviewer: after 1.0. Background and hairline in `paint.rs:17–42`, placer and focus ring inline in `BarLogic::paint` (`thread.rs:1949–1979`), pressed/active/drop-target backdrops in `BarSensors::draw` (`sensors.rs:303–349`, two blocks identical but for the brush). `render_bar` and `budget_bar_redraw` call `paint_bar` and `sensors.draw` directly, so CI's screenshots never show the placer, focus ring, active highlight or rise opacity as the bar draws them; the 247-line specimen (`paint.rs:181–427`) imitates meters and graphs by hand. `FakeWindow::invalidate` is a no-op, so none of the 33 `invalidate()` calls is asserted. **Proposal:** chrome as pure functions in `paint.rs` behind a `paint_frame` that `BarLogic::paint` calls; the fakes in a `#[cfg(test)] bar/testing.rs` so the harness drives a real `BarLogic`; drop the specimen; count invalidations.
- **B8 Low — `BarSensors` repeats lookup-and-notify and indexes zones by number.** Effort S; reviewer: after 1.0. 12 linear `find(|p| p.entry.id == id)` scans (`sensors.rs:402–621`), four followed by the same "call, mark dirty, return"; `Hit` clones the whole `SensorInstance` on every pointer move to read its id (`thread.rs:467`, 1426); zone orders `[0, 2, 1]` (`sensors.rs:304`) and `[1, 0, 2]` (353) rely on `Zone`'s declaration order; `Left, Center, Right` is spelled out again at `sensors.rs:137`, `thread.rs:1231`, `exchange.rs:23`. **Proposal:** `placed_mut(id)`, `notify(id, f)`, `hit_id(x)`; `Zone::ALL`, `Zone::index()` and named `DRAW_ORDER`/`HIT_ORDER`.
- **B9 Low — `BarWindow` mixes units, and the bar converts coordinates itself.** Effort S; reviewer: helpers after 1.0, leave the trait whole. The 21-method trait (`platform/mod.rs:1325–1400`) takes physical rects, `resize_to` a physical rect with a logical width, `BarGeometry.scale` is `f64` where canvases use `f32`; the bar converts inline at `thread.rs:93–101`, 338, 403, 419, 692, against `CLAUDE.md`'s "platform code converts". `PopupCursor` doubles as the bar's cursor. **Proposal:** `BarGeometry::{screen_x, to_physical, to_logical}` with tests; rename `PopupCursor` to `Cursor`.
- **B10 Low — the classic skin is read from disk and decoded inside `paint()`.** Effort M; reviewer: after 1.0. `BarLogic::paint` → `SkinCache::get` (`thread.rs:1924`) → `pack::load`, `read_custom`, WIC decode (`skins/mod.rs:75–173`) on the bar thread; §4.1 records this as the one exception (D76), yet `bar/icons.rs` already has a worker with a wake-up. **Proposal:** render the skin on the icons worker and draw the plain background until it arrives.
- **B11 Low — `BarHost` has 18 methods in four roles.** Reviewer: leave as is. `bar/mod.rs:40–85`: app lifecycle, 7 config edits, the sampler, main-thread UI. One impl and one fake; splitting would add plumbing without making either simpler.
- **B12 Low — dispatch scales; only the `Wake` arm holds logic.** Effort S; reviewer: with B1. `Command` (7 variants) is drained in `UiEvent::Wake` (`thread.rs:1781–1824`), collapsing a burst into one theme refresh and one sync; `UiEvent` (26 variants) has one delegating line per arm. **Proposal:** the `Wake` body into `drain`, the keyboard prelude (1770–1774) into `pointer_down`; leave the enums.
- **B13 Low — misplaced and stale doc comments.** Effort S; reviewer: before 1.0, with B1. `thread.rs:778` (`pointer_up`'s doc above `end_moving`); `hint.rs:212` (`paint`'s doc above `spoken`); `paint.rs:179` ("until the sensors draw the bar", stale); `HintFrame` and `paint_bubble` also frame popups (`BubbleFrame`); the module doc at `thread.rs:1–3` lists 5 of its 12 jobs.

## Settings, config and the app (`src/settings`, `src/config`, `ui/`, `src/app.rs`, `src/lib.rs`, `src/transfer.rs` and the other top-level modules)

### Strengths

- The pure mapping layer is tested and OS-free, as `CLAUDE.md` asks: `settings/model.rs` (`route`, `patch`, `changes`, `in_effect`, `choice_index`, …; `every_choice_matches_the_settings_model` checks `CHOICES` against the serde enums), `settings/form.rs` (14 tests, no Slint), and the pages' plain functions in `layout.rs` and `picker.rs`.
- `ConfigStore` is one write path: `update` takes all of a closure's changes or none; listeners run without the lock; a writer thread debounces and retries; writes are atomic (tmp, fsync, `.bak`, rename) and a broken file is recovered. Every writer (Settings, tray, hotkey, bar) goes through it.
- Migrations are pure `fn(Value) -> Value` steps, testable alone, guarded by `steps_cover_every_schema_below_current`.
- §11.2's storage rule is in one place (`schema::to_stored`, `sensors/schema.rs:376`).
- The dependency direction holds where it matters: the bar reaches the app only through `BarHost`; nothing in `bar`, `sensors`, `sampler`, `providers`, `platform` or `config` names `app` or `settings`; `config` depends only on `i18n`; `transfer.rs` talks to a `Dialogs` trait (15 OS-free tests).
- One i18n catalog for Rust and Slint, with a test over every `I18n.tr` key.

### Findings

- **C1 Medium — `settings/mod.rs` is a god module, and the page split is uneven.** Effort M; reviewer: after 1.0 (moving the test out: before, S). About 675 production lines with 7 jobs: lifecycle and public API (70–240), 13 generic callbacks and the page lifecycle in `connect` (243–369), `fill` for five pages (372–482), save and patch (486–540), winit hotkey recording (547–621), `apply_hotkey`, the file `pick`er (647). Appearance, Welcome, Properties, Picker and Layout have modules with their own `fill`/`connect`/`PAGE`; Applications has a 31-line module whose `fill` is in `mod.rs:479`. `on_page_changed` (255–281) hard-codes every page's leave behaviour, so a page with enter/leave behaviour means editing `mod.rs`. **Proposal:** `settings/window.rs` (lifecycle), `settings/general.rs` (the plain pages and generic `set-*`), `settings/save.rs`, `settings/hotkey_record.rs`; an optional `left(open, app)` per page called from a list; `render_settings_pages` (703–1319) to `settings/screenshots.rs`, as `accessibility.rs` already is.
- **C2 Medium — the `WINDOW` thread-local is reached 41 times outside tests, with two borrow policies.** Effort S; reviewer: before 1.0. 17 sites `borrow()`/`borrow_mut()`, which panic on re-entry (e.g. `mod.rs:489` in `save`, which then runs `fill` → `appearance::apply_scheme` → winit; the config listener at `mod.rs:173`); 24 use `try_borrow*`, which silently do nothing. Nothing says which applies where; the `WINDOW.with(|w| { let Ok(mut w) = w.try_borrow_mut() else { return }; let Some(open) = …` boilerplate repeats about 20 times. **Proposal:** `with_open`/`with_open_mut` in the window module with one documented policy (`try_borrow`, debug log when busy), replacing the 41 sites: no panicking paths, about 100 lines fewer.
- **C3 Medium — the Rust–Slint contract is coded as integers that tests only partly check.** Effort S for a test (before 1.0), M for Slint enums (after 1.0). Page numbers live in 7 Rust places (`model::PAGES`, `SENSORS_PAGE: usize`, `GENERAL_PAGE: i32`, `appearance::PAGE`, `properties::PAGE`, `picker::PAGE`, `welcome::PAGE`) and 4 Slint ones (the `Pages` global, `if SettingsState.page == 0…5` at `settings.slint:2349–2354`, the navigation list, a parallel title array): inserting a page is about 15 edits in 7 files, and only five numbers are cross-checked, inside the accessibility test (`accessibility.rs:257–272`). `RowKind::code()` is `self as i32` (`form.rs:34`) matched by `row.kind == 0…7` (`settings.slint:1983–2047`); `LineKind` and `zone as i32` likewise (`layout.rs:160`, 165), unchecked. Choice indices depend on `CHOICES`' order (`theme == 1` 11 times; 37 numeric comparisons in the file). **Proposal:** Slint `enum`s for `Page`, `RowKind`, `LineKind`, `Zone` (Rust then gets `ui::Page::Properties`); `bool` properties such as *classic* or *floating* filled by Rust instead of index comparisons. Before 1.0, one test pinning the `RowKind` codes, every `PAGE` and `PAGES` against `ui::Pages`.
- **C4 Medium — the 40 settings paths Slint passes to Rust are never validated.** Effort S; reviewer: before 1.0. `set-flag`/`set-choice`/`set-number`/`set-color`/`set-text`/`set-font`/`reset` take dotted paths (`"bar.hideOnFullscreen"`, `"popups.showDelayMs"`); a typo shows only at runtime as "unknown settings" (`patch.rs:37`) in the save banner. **Proposal:** a test beside `every_key_used_in_the_slint_ui_exists` (`i18n.rs:93`) that every such path resolves in `Settings::default()` and every `set-choice` path is in `CHOICES`.
- **C5 Medium — the value in effect of theme-dependent settings is resolved in four places.** Effort M; reviewer: after 1.0, before if S15 adds theme-dependent settings. `Settings::bar_height()` (`config/model.rs:435`) is the only accessor; `bar/theme.rs:65–80` repeats `unwrap_or(d.…)` and recomputes what `Settings::light_bar` does; `settings/model.rs:224–249` `in_effect` has 11 arms keyed by path string; `settings/mod.rs:455–466` repeats `popups.opacity.unwrap_or(…)`; `appearance.rs:242–254` clones `Settings` with `color: None` to ask the theme's colour. A new theme-dependent setting touches `ThemeDefaults`, `in_effect`, `Theme::resolve`, three `fill` setters, a Slint property trio and a `WithReset` row. **Proposal:** `Settings::effective(os_dark) -> Effective` in `config/model.rs`, a flat struct of resolved values with the same camelCase paths; `in_effect`, `Theme::resolve` and `fill` read from it.
- **C6 Medium — `Form` builds each list field's options twice and plumbs machine lists by hand.** Effort S; reviewer: after 1.0. `Form::row` (`form.rs:191–325`) and `Form::choose` (342–383) each compute options for the same 8 field kinds and must agree on index rules (`Font`: `skip(1)` + 1 in `row`, index 0 → `""` in `choose`); both end in wildcards (`_ => {}` at 320, `_ => None` at 379), so a new list `FieldKind` compiles and shows an empty list. Volumes and batteries pass through 4 layers twice (`app.rs:74–80` → `settings::volumes_changed`/`batteries_changed` → `properties::…` → `Form::set_*`); `font_options` (`form.rs:443`) duplicates `model::font_labels` (`model.rs:185`). **Proposal:** one exhaustive `choices(field)` used by `row` (position) and `choose` (nth); a `MachineLists` struct with one `set_list` entry.
- **C7 Medium — `app.rs` and `settings` depend on each other; the main-thread UI flows are split over three modules.** Effort S–M; reviewer: after 1.0. `App`, the state shared by all threads, calls `settings::volumes_changed`/`batteries_changed` (`app.rs:77–78`), `settings::activate`/`open` (318, 331) and builds `NativeDialogs { owner: settings::owner() }` twice (401, 411; again in `welcome.rs:109`); `watch_lists(volumes: bool, batteries: bool)` (`app.rs:98`) takes flag parameters; `transfer.rs` is a main-thread UI flow at the top level. **Proposal:** Settings passes its own sink when it subscribes; `transfer.rs` moves to `settings/transfer.rs` behind `settings::import_layout`/`export_layout`, so `AppHost` only hops threads.
- **C8 Medium — `ui/settings.slint` is one 2,367-line file with a 131-member global and repeated row boilerplate.** Effort M; reviewer: after 1.0. 23 components, 5 structs, 2 globals; `SettingsState` alone is 214 lines (91 properties, 40 callbacks). 11 switch rows, 21 combo boxes and 9 sliders each repeat ~10 lines, writing the label key twice (`accessible-label: I18n.tr(` 38 times). **Proposal:** `ui/settings/state.slint`, `controls.slint` (with `SwitchRow`/`ChoiceRow` taking the key and the path) and `pages/<page>.slint`, the window left alone in `window.slint`; perhaps one global per page. Caveat: the i18n key test reads `ui/` non-recursively (`i18n.rs:108`), so it must recurse in the same change or the moved pages lose their check silently.
- **C9 Medium — the Settings glue's behaviour is tested only inside a 615-line ignored screenshot test.** Effort M; reviewer: after 1.0. `render_settings_pages` (`mod.rs:705–1319`, `#[ignore]`) holds 49 assertions on saves, the properties form and the picker; `cargo test` never runs them (only CI's `--ignored` step), and `save`, `apply`, `save_change` have no other test. It also rebuilds `Open` as a literal (721–731) duplicating `create()`. **Proposal:** the behavioural checks as normal tests on Slint's testing backend (as `accessibility.rs` does) in `settings/tests.rs`; the ignored test only renders; `Open::new`.
- **C10 Low — `ConfigError` has no stable code and its English text reaches the UI.** Effort S; reviewer: before 1.0. §4.5 says errors carry a code and a message; `ConfigError` (`config/mod.rs:15`) is `Io`/`Json`/`Invalid(String)` with "no sensor {id}", "unknown sensor type …" (`ops.rs:17`, 55), "unknown settings: …" (`patch.rs:37`), shown as they are in 5 places (`mod.rs:499`, `picker.rs:255`, `properties.rs:250`, `layout.rs:186`, `transfer.rs:72`), while import, skin and pack errors are localised. **Proposal:** variants (`NotFound`, `UnknownType`, `UnknownSettings`, `Invalid`) with `code()` and a localised `message()`.
- **C11 Low — every config change refills the whole Settings window.** Effort S; reviewer: after 1.0. The listener (`mod.rs:166–180`) ignores `old` and runs `fill` and `layout::fill` for any change, including a sensor's `state` written by the bar; each refill rebuilds the font model, lists monitors (an OS call, `mod.rs:396`), materials and skin tiles. **Proposal:** refill only what changed (`settings`, `layout`).
- **C12 Low — routes are strings built in the bar and parsed back in Settings, though `Route` is a typed enum.** Same as B6.
- **C13 Low — Settings' file pickers bypass `Dialogs`, and window-handle code sits in the properties page.** Effort S; reviewer: before 1.0. `pick()` (`mod.rs:647`) and `browse()` (`properties.rs:256–290`) call `platform::pick_path` directly, each building a `PathRequest`; `transfer.rs` uses `Dialogs::open_path`. `properties::owner` (`properties.rs:316`) is `#[cfg(windows)]` raw-window-handle code outside `platform/`, used by `mod.rs:141`. **Proposal:** one `settings::dialogs()` in the window module for all three pickers, testable with a fake.
- **C14 Low — `ConfigStore` runs callers' closures under its mutex, and `get()` clones the whole config.** Effort S; reviewer: after 1.0. `update` (`store.rs:123`) runs `f` locked; `App::add_sensor` → `ops::add` fills machine defaults inside it, so `DiskMeter::machine_defaults` lists volumes (`sensors/disk.rs:156`, with device queries) while every `get()` waits. `get()` deep-clones `Config` (48 calls in `settings/`, `transfer.rs`, `hotkey.rs`, several per `fill`). **Proposal:** compute machine props before `update`; store `Arc<Config>`.
- **C15 Low — polish.** Effort S; reviewer: before 1.0. Misplaced docs (`settings/model.rs:277`: `monitor_choices`' doc on `floating_with_width`; `form.rs:430`: `font_options`' doc on `power_modes`); `config::model::Theme` clashes with `bar::theme::Theme`, so 5 files import `Theme as ThemeId` (rename the config enum `ThemeId`, serde unchanged); `settings/model.rs` holds UI mapping helpers under the same name as `config/model.rs` (`settings/mapping.rs`); `lib.rs:21–29` makes seven modules `pub` whose only outside user is `main.rs` calling `run()` (private modules let the compiler report dead `pub` items).
- **C16 Low — main-thread service state lives in module statics.** Reviewer: leave as is. `hotkey::STATE`/`MANAGER`, `autostart::ERROR`, `transfer::BUSY`, `settings::WINDOW`; `fill` reads `hotkey::error()` and `autostart::error()` as hidden inputs. They are process and main-thread singletons; moving them onto `App` adds plumbing for little gain.

## Across areas

Notes the reviewers made at their area's boundary; each becomes part of an area's finding or a finding of its own when the plan is made.

- **C-x1 — Settings depends on bar internals** (`bar::skins`, `bar::theme::Theme`, `bar::skin_preview`; skins read and previews rendered on the main thread). See B2.
